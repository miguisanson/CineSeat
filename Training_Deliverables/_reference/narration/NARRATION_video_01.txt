Every iOS app you've ever used — the one that books your rides, the one that plays your music — comes down to the same handful of foundations. A language, a set of tools, and a way of connecting what's on screen to code that runs. That's this module.

Here is what you will be able to do by the end of this video.

Let's start with what iOS development is. It means building for Apple's platforms — iPhone, iPad, Apple Watch, Apple TV. The language is Swift.

A little history helps here. Before Swift, Apple development was done in Objective-C, and you'll still meet that in older codebases. Swift was announced on the second of June, twenty fourteen. Then in twenty nineteen came SwiftUI, a newer, declarative way of building interfaces.

This course teaches Swift with UIKit, not SwiftUI, and here is why. UIKit is what the overwhelming majority of existing production code is written in. And doing layout by hand in UIKit first is what makes SwiftUI's shortcuts legible instead of magical. You'll understand what's being done for you, because you'll have done it yourself.

To build anything you need a Mac, Xcode, and a free Apple account. Xcode is the whole toolkit — editor, interface builder, simulator, debugger.

When you create a project the template asks for several things. Most you can accept. Two you should not rush.

The first is the bundle identifier. That's your app's unique identity on the App Store, and no two apps can share one. If somebody else registers yours, you cannot simply take it — it can only be transferred by agreement between accounts. Pick it deliberately.

The second is the interface: choose Storyboard, not SwiftUI, because that's what selects UIKit.

Xcode then generates a handful of files. AppDelegate, SceneDelegate, a storyboard, and a view controller. Don't delete any of them. AppDelegate in particular is the first thing that runs when your app opens.

The language. Swift has two ways to declare a value, and the distinction matters. 'var' is a variable — it can change. 'let' is a constant — once it's set, that's it.

Reach for 'let' by default and only use 'var' when you need to change the value. It isn't pedantry: a constant is a promise to everyone reading your code that this thing will not move.

The core types: Int for whole numbers, Double for decimals, String for text, Bool for true or false. Then two collection types you'll use constantly — Array, an ordered list you reach into by index, and Dictionary, key-value pairs you reach into by key.

Control flow is conventional. if-else, switch, for loops, while loops. One small difference if you're coming from another language: Swift doesn't need parentheses around the condition.

Functions use the 'func' keyword, a name, typed parameters and an optional return type. One naming convention marks your code as idiomatic: camelCase. First word lowercase, every following word capitalised. Not snake_case with underscores.

The single most important idea in this module: Optionals.

Look at this model from the real app. Three of its properties have a question mark after the type. That question mark means: this might hold a value, or it might be empty.

Why does that exist? Because most crashes in a mobile app come from data. You expect a field, the data doesn't have it, and the app dies in someone's hand. Optionals force you to confront that possibility at the moment you write the code, rather than discovering it in production.

You have safe ways to open an optional. 'if let' unwraps it only when there's something inside. The double question mark supplies a fallback value. And 'guard' exits early when the value is missing.

There's also an exclamation mark, which force-unwraps and asserts the value is definitely there. Use it sparingly. Every force-unwrap is a small bet that you're right, and a crash if you're wrong.

Two more language pieces before we finish. A struct is a value type — it gets copied. A class is a reference type — it gets shared. The practical rule this course follows: structs for data and models, classes for behaviour and services.

And a protocol is a contract. It says what a type must be able to do, without saying how. That sounds abstract now; in Module six it becomes the backbone of the whole architecture.

Last topic, and it's the practical one. How does a button on screen run your code?

There are two separate connections, and you usually need both. An outlet connects the control as an object, so code can reach in and change it — enable it, restyle it, read its text. An action connects the behaviour, so code runs when it's tapped.

You make both by holding Control and dragging from the control into your code. Outlets go above viewDidLoad. Actions go below it. Mixing those two up is behind a whole family of beginner bugs.
