The key insight is that there is no single right answer. iOS gives you several mechanisms deliberately, and the skill is matching each to the weight and sensitivity of your data. Get that wrong and your app is either slow or insecure.

First, UserDefaults. Key-value storage for small, lightweight things — which filter was last selected, whether the user has seen the welcome screen. You set a value with a key and read it back with the same key.

One rule: the type must match. Save a Bool and read it as a String and you'll get an error. A naming habit that prevents this — prefix boolean keys with 'is' or 'has', so the key itself reads as a yes-or-no question.

Second, FileManager. When your data is bigger and structured, you encode it as JSON and write it to a file in the app's Documents directory.

This is how the reference app stores bookings, profiles and reviews. Codable turns the model into JSON, FileManager writes it, and on next launch it reads straight back into the same types.

Third, Core Data. This is Apple's heavyweight option — a full object graph with entities, attributes and relationships. You'd reach for it when you have relational data, or a large offline dataset that syncs later.

The reference app deliberately doesn't use it. For this volume of data, JSON files were simpler and easier to reason about. I'd flag that as a real skill: knowing when not to reach for the heavy tool is as valuable as knowing how to use it.

And now the fourth, which is the most important part of this module. The Keychain.

There's a belief that circulates that UserDefaults is encrypted on iOS, so it's fine for passwords and tokens. That is not true,

UserDefaults writes to a plain, unencrypted file inside your app's container, with no access control. Anyone with file system access, or an unencrypted device backup, can read it in seconds.

Passwords, tokens, API keys, anything personal — those go in the Keychain, which is encrypted and protected by the operating system itself.
