Two kinds. Unit tests are fast because they never launch the app — they check logic directly. U I tests are slower: they launch the real app and tap it like a person would. You want lots of the first and a handful of the second.

It creates a view model. Sets the search text. Checks the filtered result. Flips the sort order. Checks the order changed. That's the whole shape: arrange, act, assert.

There's no storyboard in this test. No screen. No U I Kit at all. That's only possible because the search and sort logic lives in the view model rather than the view controller.

If that logic had stayed in the screen — the way a first calculator is usually written — this test could not exist. Testability isn't something you add later. It's a consequence of how you structured the code.

Think about what testing login would mean without this. Writing real files to disk. Storing real passwords. Making real network calls. Slow, unreliable, and dependent on an internet connection. This is the concrete payoff of dependency injection.

And this is a U I test. The app is being driven automatically — tapping a category, opening a film, checking the reviews screen, moving to seat selection.

One technique here worth stealing. This test asserts that a button is NOT present. Reviews can only be written from a booking, so the write button must never appear while browsing. Checking that something is absent is often more valuable than checking it's there.

Two practical notes for U I tests. Use accessibility identifiers rather than matching on visible text, so your tests don't break when copy changes — and your app becomes more accessible as a side effect. And always wait for an element to exist rather than asserting immediately, or you'll get tests that fail at random.

Something worth noticing about the whole suite: read the test names in order and you have the specification for the feature. Ownership. Confirmation. Showtime passed. One review per item.

No comments, no separate document. And unlike a document, a test name can't go stale — because when it stops being true, it fails.
