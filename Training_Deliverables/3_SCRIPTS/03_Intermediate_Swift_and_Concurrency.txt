This is the shortest module in the course and the most conceptually demanding. It covers the language features that separate code that works from code that scales — and, critically, how to stop your app freezing while it waits for something.

Here is what you will be able to do by the end of this video.

First, closures. A closure is a self-contained block of code you can pass around like a value. If you wrote a computed property in the last module, you've already written one.

There's a distinction worth knowing: escaping versus non-escaping. A non-escaping closure runs and finishes inside the function. An escaping one outlives the function call — it's stored somewhere and called later. Network callbacks are escaping.

Why care? Because if you do slow work synchronously, the interface freezes while it waits. The user thinks your app has hung. Escaping, asynchronous work is what keeps the screen alive.

Next, three operations you'll reach for constantly. And I want to be precise here, because these get confused.

Map transforms. It runs a closure on every element and gives you back a collection of the same length. It does not search.

Filter selects. It keeps the elements matching a condition, so you get a shorter collection.

Reduce collapses. It folds a whole collection down into one value.

And if you want to find something, that's a fourth operation — first-where. Worth separating those in your head now, because mixing up map and search is a very common early confusion.

Here they are doing real work: this filters the movie list by the search text, then sorts the result by rating. Two operations, chained, replacing what would otherwise be a couple of loops and a temporary array.

Now memory. Swift uses Automatic Reference Counting — A R C. It counts how many things are holding onto an object, and frees it when nothing is.

A strong reference keeps an object alive. A weak reference doesn't, and is automatically set to nil when the object goes away. There's also 'unowned', which doesn't retain and is never nilled — so if you access it after the object is gone, you crash. Prefer weak.

The problem this prevents is a retain cycle: two objects each holding the other strongly, so neither can ever be freed. That's a leak.

One habit prevents most of them. When you write a closure that captures self, mark it 'weak self' by default. It costs nothing when unnecessary and saves you when it isn't. Here it is in the real app.

Finally, concurrency. There's one rule and everything follows from it. Background threads do the waiting. The main thread does the drawing.

Long work — fetching data, downloading images — goes on a background thread. But every single U I update must come back to the main thread. Update the interface from a background thread and you get undefined behaviour and crashes.

The older way of doing this is Grand Central Dispatch, and you'll see it in existing code. The modern way is async and await. 'await' means: pause here, let everything else keep running, and continue when the result arrives. It's much easier to read than nested completion handlers.

Now the part of this module that isn't code. Before you build anything real, you plan it — and there's a four-step workflow worth adopting.

Requirements first: list every feature, unfiltered. Then a flowchart: turn those into paths and decisions. Then a wireframe: sketch what each screen holds. Only then, code.

This is the flowchart for the reference app. Notice what's interesting about it — it isn't the happy path. It's the branches. Not signed in. No seat selected. Cancel and release the seats. Those branches are where bugs live, and drawing them before you write code is the entire point.

The professional argument is simple: when your app gets tested, every path gets walked, including the awkward ones. If you already mapped them, testing finds nothing you didn't anticipate. A flowchart is defect prevention, not paperwork.
